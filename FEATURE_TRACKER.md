## ⏪ Phase 1 / Base Architecture (Pre-Progress 2)

### 💾 Data & State Management
- [x] **External JSON State Persistence:** Game state (Party & Enemies) is loaded and saved dynamically via `data/campaign.json` using the `DataManager`, avoiding hardcoded stats.
- [x] **Bidirectional TOON Serialization (Token-Oriented Object Notation):** A custom serialization pipeline (`TOONConverter`) drastically reduces API overhead. State is compressed into TOON before sending to the Arbiter. Furthermore, all LLM API outputs (including Intent Routers and Arbiter logic) are explicitly forced via system prompts to return 1-line TOON (`key:value|key:value`), completely eliminating verbose JSON outputs. This achieves ~50% total token reduction and lower latency.
- [x] **Decoupled Health vs. Tactical Conditions:** The `Character` model strictly separates Health Status (e.g., Unscathed, Bloodied, Critical) from Tactical Conditions (Enum: `NORMAL`, `STUNNED`, `BLINDED`), ensuring narrative damage doesn't overwrite mechanical penalties.
- [x] **Dual-Stream Memory & Context Collapse (State-Dependent Pruning):** Upgraded the sliding window into a two-tier system: `combat_memory` (maxlen=10) and `story_memory` (maxlen=5), both fully configurable via `settings.json`. Implemented an automatic interception hook on `VICTORY` or `FLEE` states that feeds the raw combat logs to an LLM Summarizer. The AI compresses the mathematical battle into a single narrative sentence, pushes it to `story_memory`, and flushes the combat queue. This architecture prevents token bloat and ensures NPCs do not hallucinate game mechanics (like AC or HP) during subsequent roleplay phases.
- [x] **Static Lore Injection (Static RAG):** Implemented a fail-safe retrieval system that loads world-building context from `data/world_lore.txt`. This allows for instant "World Flavor" shifts (e.g., Aethelgard setting) without code changes. The engine handles missing lore files with a hardcoded fallback to ensure the Narrative Generator remains grounded and consistent.
- [x] **Robust Backend Configuration (`settings.json`):** Abstracted hardcoded variables into an open-source-friendly JSON config file. Exposes core engine parameters (max history events, fuzzy match strictness, default DCs) and LLM API settings (model selection, temperatures). Built a bulletproof boot sequence in the `DataManager` that utilizes hardcoded Python fallbacks to automatically repair missing or corrupted config files, preventing engine crashes for end-users.
- [x] **Persistent Campaign Journal (System Log):** Implemented an append-only logging system that permanently records every player input and AI output in real-time to a local file. Includes an auto-reset mechanism triggered during new game boots (via `DataManager.clear_log()`) to ensure fresh sessions do not inherit legacy history. This creates a parseable, irreversible script of the adventure and lays the groundwork for future save/load summarization.

### 🧠 The Intent Router (Two-Path Architecture)
- [x] **Path A (Fixed Rules Routing):** Standard RPG mechanics (Attack, Move) bypass the LLM for calculation, sending the action directly to the Python `RulesEngine` to mathematically guarantee zero AI hallucinations.
- [x] **Path B (Creative Improv Routing):** Complex user prompts (e.g., "I throw sand in his eyes") are intelligently routed to the `LLMService` (Arbiter), which judges logical feasibility, assigns a DC (Difficulty Class), and automatically outputs a Symbolic Side Effect (e.g., `BLINDED`).
- [x] **Dynamic Action Sequencing (`FIXED_COMBO`):** The LLM parses multi-step user intents (e.g., "I shoot him and then run away") and extracts an `action_order` array. The game engine dynamically executes the sequence exactly as the user typed it, rather than forcing a rigid turn structure.
- [x] **Action Fairness & Economy Guard:** The engine intelligently handles invalid actions. If an Arbiter denies a creative narrative request, the turn is refunded. However, if a player makes a mechanical error (e.g., attacking out of range), the action fails and the turn is rightfully consumed, preventing "free move" exploits.
- [x] **Action Fairness & Multi-Agent Economy Guard:** The engine strictly enforces a 5e-style action economy. The `Character` model now tracks `has_acted` and `has_moved` boolean flags, which are automatically refreshed via `reset_turn()` at the start of every combatant's turn. Inside `intents.py`, the engine asserts these permissions before execution: illegal move requests or double-attacks are deterministically denied, ensuring the AI cannot exploit the "freeform" nature of the prompt.

- **Human-Readable Exit Display (Node Name Resolution):** Upgraded `render_exploration_dashboard()` in `exploration_ui.py` to accept `quest_data` and resolve raw node IDs (`node_01`, `node_02`) into their display names (`Mine Entrance`, `Main Shaft`). *Engineering Justification:* Showing internal database IDs to the player breaks immersion and forces them to memorize technical identifiers. Resolving to names directly from the quest graph provides a natural, roleplaying-friendly navigation experience.
- **Smart Description Truncation (Hub Dashboard):** Fixed the Hub quest board to only append `...` when a description exceeds the display limit (80 chars), instead of unconditionally appending it to all descriptions regardless of length. *Engineering Justification:* Minor cosmetic fix that prevents short, complete descriptions from appearing artificially cut off.
- **Loading Indicator for LLM Classification:** Added a `Thinking...` carriage-return indicator in `game_loop.py` before the hybrid exploration classifier fires. Covers the 1-2 second window when the Smart Router's LLM pass executes on complex natural-language inputs. *Engineering Justification:* Without visual feedback, the terminal appears frozen during LLM inference, creating a perception of lag or crash — particularly damaging during a live thesis demo.

### 🧪 Pilot Playtest Bug Fixes (Casual Persona Feedback)
- **USE Item Self-Target Resolution (Critical):** Fixed a fatal bug where the `USE` action handler in `intents.py` failed to recognize self-targeting commands. The LLM Intent Router would return `target:player1` or `target:bob` for commands like "use potion," but `_find_target()` only searched the enemies list — resulting in `⚠️ You and the party don't seem to have a 'player1'` while the player died holding the item. Implemented a Self-Target Guard that checks if the target matches the player's name, ID, or common aliases (`self`, `me`, `player1`), then auto-resolves to the most likely consumable item (e.g., Healing Potion) from their inventory. *Engineering Justification:* Self-use is the most common use case for potions and healing items. The engine must gracefully handle the fact that the LLM returns a character reference instead of an item name — this is an inherent LLM output ambiguity that requires a deterministic Python interception layer.
- **Narrator Node ID Sanitization (Critical):** Fixed the `narrate_room_entry()` and `narrate_exploration_look()` prompts in `narrator_agent.py` that were injecting raw node IDs (e.g., `node_01`, `node_05`) into the LLM's context as "VALID EXITS." The LLM faithfully parroted these IDs in its narration (e.g., "You see exits leading to node_01 and node_05"), completely breaking immersion. Both methods now accept `quest_data` and resolve node IDs to their human-readable display names (e.g., "Mine Entrance", "Supply Depot") before building the prompt. Added an explicit instruction: `Do NOT use internal IDs like 'node_01'. Always use the room NAMES.` *Engineering Justification:* The LLM is a text-completion model — it will reproduce whatever tokens appear in its prompt. Passing sanitized, player-facing names instead of internal database IDs is a fundamental grounding requirement to prevent data-layer leakage into the narrative layer.
- **Context-Aware Node Cleared Narration (Puzzle vs. Combat):** Fixed the `narrate_node_cleared()` method in `narrator_agent.py` which always used a combat-oriented prompt ("The player has just won a combat encounter"), even when called after a puzzle solve. This caused the LLM to narrate "defeated foes" and "the smell of blood" in rooms where no combat occurred. Added a `cleared_by` parameter (`"combat"` or `"puzzle"`) that switches between two distinct prompts — combat victories describe aftermath and silence, while puzzle victories describe the obstacle clearing away. The game loop now explicitly passes `cleared_by="puzzle"` from the puzzle success path. *Engineering Justification:* A single narration template for two fundamentally different event resolutions causes narrative dissonance — the hallmark of a poorly grounded AI system. Branching the prompt by event type is essential for the LLM to generate contextually accurate flavor text.
- **Structured Campaign Log with Phase Headers:** Overhauled the campaign log formatting from flat, unstructured `[TAG] text\n` lines to a visually organized document with clear phase separators (`═══ HUB ═══`, `─── EXPLORATION ───`, `⚔️ COMBAT ⚔️`, `🧩 PUZZLE`). Added `DataManager.append_phase_header()` which is called at every phase transition in the game loop — Hub entry, quest start, combat bridge, and puzzle encounters. *Engineering Justification:* The raw campaign log is the primary data artifact for thesis evaluation. A wall of unstructured text makes it extremely difficult to identify which events occurred in which game phase, complicating both manual review and automated analysis. Phase headers create a machine-parseable and human-readable record of the full gameplay session.
- **Debug Mode Parity for Exploration:** Extended the `DEBUG_MODE` toggle (previously only available in the Combat Loop) to the Exploration Loop. The exploration loop now reads the initial debug state from `settings.json` on entry, supports the `debug` command to toggle on/off mid-exploration, and prints diagnostic information (`🤖 [Router] type:MOVE | target:Main Shaft`) showing the exploration classifier's output. *Engineering Justification:* Without debug prints, developers have zero visibility into the hybrid router's decision-making during exploration. When the LLM fallback fires on ambiguous input, the developer needs to verify whether the regex or the LLM handled it, and what target was resolved — essential for diagnosing misrouting issues like the ones found during the pilot playtest.
- **Class Abilities Not Loading (Critical):** Fixed a critical bug where class abilities (Pray, Second Wind, Smite, Lay on Hands, etc.) were defined in the premade JSON templates (`data/premade/characters/*.json`) but **never loaded** into the Character object during `initialize_new_game()` in `startup.py`. The `Character()` constructor call was missing the `abilities` parameter entirely, so every new character was created with `abilities: []` despite the JSON templates containing full ability definitions. Added ability parsing logic (JSON dicts → `Ability` objects with `RechargeType` enum) and wired it into the constructor. *Engineering Justification:* Abilities are core to every class archetype — a Cleric without Pray or a Fighter without Second Wind has no unique mechanical identity, reducing gameplay to basic attacks only and invalidating the class system entirely.
